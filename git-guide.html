1. Git 是什么

Git 是分布式版本控制系统：记录项目每次变更、支持多人并行开发、可回退到任意历史版本。

对比项 说明
本地仓库 你电脑上的完整历史（.git 目录）
远端仓库 GitHub / GitLab / Gitee / 公司 Git 服务器上的副本
工作区 你正在编辑的文件
暂存区 git add 之后、等待提交的区域
版本库 git commit 之后永久保存的提交记录（在本地仓库 .git 里）

1.1 关系示意图

结合上表，记住三点即可：

  1. 工作区是你直接编辑的文件；git add → 暂存区 → git commit → 版本库。暂存区与版本库都在 .git 里，合起来就是本地仓库。
  2. 远端仓库在服务器上，用 push / pull / fetch 与本地版本库同步。
  3. 具体命令按场景查 9.2 常用命令。

2. 核心概念

2.1 提交（Commit）

提交就是把当前暂存区里的改动正式记入版本历史，生成一条带编号的记录（commit）。每条记录里通常包含：改了哪些文件、作者、时间、以及一段文字说明（commit message）。

可以把一次提交想成「给项目当前状态拍一张存档照片」——以后可以回到这一刻查看或恢复。说明里宜写清做了什么、为什么；一次提交尽量只解决一件事。

2.2 分支（Branch）

从某次提交分出的独立开发线。本文用 develop 作集成分支；实际项目也可能是 main / master 等，以团队规范为准。

读图： 圆角框 A～F 表示六次 提交（commit） 的代号，仅用于示意。箭头方向为时间推进（从左到右越新）。

代号 含义（结合上图）
A、B、C develop 上较早的提交
B → D 从 B 拉出功能分支（git switch -c feature/iot-20260815）
D、E 在功能分支上的新提交
E → F 合并回 develop 后，F 代表合并完成后的进展（D、E 的改动已进入 develop）

2.3 远端与跟踪

  • Remote：本地给远端起的别名，默认多为 origin。
  • origin/develop：远端 develop 在本地的跟踪引用（Fetch 后更新）。
  • 本地 develop：你当前正在使用的分支，可与 origin/develop 一致、领先或落后。
  • 跟踪分支：本地分支可跟踪远端分支（如 develop 跟踪 origin/develop），Pull/Push 时知道与谁同步。

3. 本地基本流程

修改文件 → add（暂存）→ commit（提交）→ push（推送到远端，可选）

Commit 只写在本地；别人要看到你的改动，需要 Push。status / add / commit / pull / push 见 9.2「日常」。

4. 远端与同步：Fetch / Pull / Push

4.1 三者对比（对应 TortoiseGit 菜单）

操作 英文 做了什么 会不会改你当前分支上的文件
获取 Fetch 下载远端最新提交到本地引用（如 origin/develop） 一般不会自动改工作区
拉取 Pull Fetch + 合并（或 Rebase）到当前分支 会，把远端变更合进来
推送 Push 把本地已提交的历史上传到远端 改的是远端，不是本地文件内容

记忆：Fetch = 只看远端更新了什么；Pull = 接到当前分支；Push = 上传本地提交。

4.2 Sync（同步）

在 TortoiseGit / 部分客户端里，常表示 Pull + Push 组合。具体以工具提示为准。

4.3 推荐习惯

场景 建议
开始干活前 Pull
功能做完 Commit → Push
不确定远端有什么 先 Fetch，在日志里对比再决定是否合并
有未提交修改又要 Pull 先 Commit 或 Stash，再 Pull

4.4 Clone

首次把远端仓库完整复制到本机（含历史）。之后在同一目录用 Pull/Push 即可。命令与按分支克隆见 9.2「克隆」。

5. 分支与合并

5.1 为什么要分支

集成分支（如 develop）保持稳定；功能在独立分支（如 feature/iot-20260815）开发，完成后再合并。

5.2 常用操作去哪查

你想做的事 说明
查看分支 9.2「查看」；git branch / git branch -a
新建功能分支、切换、合并 9.2「分支」；switch / checkout 新旧写法见 9.1
变基（可选，高级） 在功能分支上 git rebase develop 可使历史更线性；勿对已推送且他人共用的分支随意 rebase

5.3 Merge vs Rebase（简版）

Merge Rebase
结果 多一个合并提交，历史分叉可见 历史更呈一条线
风险 较低，适合共享分支 可能改写已发布历史，需团队同意

6. Pull Request（PR）工作流

PR（GitLab 上常叫 MR）= 请求把某分支的改动合并进目标分支（本文为 develop），并附带说明与审查。

6.1 典型流程

1. 在 develop 上 Pull 最新 → 建分支 feature/iot-20260815
2. 本地开发 → commit（可多次）
3. push feature/iot-20260815 到远端
4. 网页创建 PR（feature/iot-20260815 → develop）
5. Review、CI
6. 合并 PR
7. 其他人本地 develop Pull，拿到结果

6.2 PR 里有什么

文件 diff、描述与 Issue、评论与审批、CI 结果。

6.3 直接 Push develop 还是走 PR

方式 适用
直接 Push develop 个人项目或团队允许
PR 再合并 团队项目、需要审查（推荐）

7. 常见协作模型

7.1 功能分支（推荐）

每人或每需求一条分支，合并走 PR。本文示例即 develop + feature/*。

7.2 其他模型（了解即可）

  • Git Flow：除 develop 外还有 main 发布线、release/*、hotfix/* 等。
  • Fork：开源贡献时 Fork 到自己仓库，改完后 PR 回原仓库。

8. TortoiseGit 速查

在资源管理器右键 TortoiseGit：

菜单项 作用
Clone 首次克隆远端仓库
Pull / Fetch / Push 拉取、仅获取、推送（含义见 §4.1）
Commit 提交
Show log 历史与分支
Create branch / Switch/Checkout / Merge 分支与合并
Diff 对比差异

右键菜单：常勾 Pull、Push、Commit；需要「先看再合」可加 Fetch。

9. 命令行速查

本章是命令的唯一详细清单；前文各节只讲概念与流程，需要敲命令时以 9.1、9.2 为准。

9.1 新写法与旧写法（按 Git 版本）

从 Git 2.23（2019 年 8 月）起，将原 git checkout 的部分职责拆为 git switch（分支）与 git restore（恢复文件）：

场景 新写法（推荐） 旧写法（仍普遍可用） 自版本
切换到已有分支 git switch <分支> git checkout <分支> 2.23
新建并切换到分支 git switch -c <新分支> git checkout -b <新分支> 2.23
丢弃工作区里某文件的修改 git restore <文件> git checkout -- <文件> 2.23
取消暂存（改动仍留在工作区） git restore --staged <文件> git reset HEAD <文件> 2.23
查看当前分支名 git branch --show-current git rev-parse --abbrev-ref HEAD 2.22

本机版本：git --version。clone / merge / pull / push 无上述新旧之分。Git 2.28+ 新建仓库默认首分支常为 main；若团队以 develop 为准，可 git config --global init.defaultBranch develop 或 git clone -b develop <url>。

9.2 常用命令

按场景列命令；分支切换的新旧写法见 9.1。

配置（首次）

  • 设置全局用户名（写入本机配置，显示在每次 commit 的 Author）

    git config --global user.name "你的名字"

  • 设置全局邮箱（建议与 GitHub/GitLab 账号邮箱一致）

    git config --global user.email "你的邮箱"

克隆

  • 下载完整仓库到本机，默认远程名为 origin；克隆完成后，工作区对应远端默认分支（不一定是 develop）

    git clone <url>

  • 克隆完成后就在 develop 分支上（远端须已有该分支）

    git clone -b develop <url>

  • 只拉取 develop 的历史，不下载其他分支引用（体积更小）

    git clone --single-branch -b develop <url>

  • 克隆完成后就在 feature/iot-20260815 分支上

    git clone -b feature/iot-20260815 <url>

  • 进入 clone 生成的项目目录（通常为 URL 路径最后一段目录名）

    cd <项目目录>

日常

  • 查看当前分支、工作区与暂存区有哪些变更

    git status

  • 把当前目录下已跟踪文件的修改及新文件加入暂存区

    git add .

  • 把暂存区内容记录为一次本地 commit（尚未传到远端）

    git commit -m "说明"

  • 从已关联的远端分支拉取更新并合并到当前分支（会改动工作区文件）

    git pull

  • 把当前分支上已 commit、尚未上传的提交推送到远端（需已配置上游，如 origin/develop）

    git push

分支（切换见 9.1）

  • 从当前所在提交新建并切换到 feature/iot-20260815（惯例：先 git switch develop，且没有未提交修改）

    新 ≥2.23 git switch -c feature/iot-20260815

    旧git checkout -b feature/iot-20260815

  • 把当前分支切换到 develop（若有未提交修改，可能需先 commit 或 stash）

    新 ≥2.23 git switch develop

    旧git checkout develop

  • 先切换到 develop，再把 feature/iot-20260815 合并进来（执行 merge 时当前分支应是 develop）

    git merge feature/iot-20260815

查看

  • 查看当前分支最近 10 条提交（哈希缩写 + 说明）

    git log --oneline -10

  • 工作区相对暂存区的差异（暂存区为空时，相当于相对最近一次 commit）

    git diff

  • 查看 remote 名称及 fetch / push 使用的 URL

    git remote -v

10. 冲突与回退

10.1 合并冲突（Conflict）

两人改同一处，Git 无法自动合并，会标记冲突：

<<<<<<< HEAD
你的内容
=======
对方内容
>>>>>>> feature/iot-20260815

处理：编辑保留正确内容 → 删除标记 → add → commit。预防：勤 Pull、小步提交、按模块分工。

10.2 暂存修改（Stash）

临时切换分支又不想提交半成品：

git stash
git switch develop
git stash pop

（switch 旧写法：git checkout develop，见 9.1。）

10.3 撤销（谨慎）

restore / checkout -- / reset HEAD 的新旧写法见 9.1。

需求 命令（示例）
未 add 的修改丢弃 git restore <文件> 或 git checkout -- <文件>
已 add 未 commit（只取消暂存） git restore --staged <文件> 或 git reset HEAD <文件>
改最后一次 commit 说明 git commit --amend（未 push 或团队允许）
回退到某次提交（本地） git reset --hard <commit>（会丢未备份的改动）

已 Push 的历史勿随意 reset --hard 后再 强制推送；优先用 revert 生成一条「反向提交」来撤销改动。

12. 最佳实践与避坑

  1. 开始改代码前先 Pull（§4.3）。
  2. 提交信息可读；不要提交密钥与大文件（用 .gitignore）。
  3. 保护好 develop：功能做完后通过 PR（合并请求） 合入，由他人审查；合并前尽量让 CI（自动跑测试/检查） 通过。不要对 develop 做 强制推送（git push --force），否则会覆盖远端已有提交，影响他人。
  4. 功能分支命名清晰（如 feature/iot-20260815），合并后及时删除远端分支（若团队有此规范）。
